<interfaces>
All five GET routes accept `cursor?: string` and `limit?: string`. Route schemas reject malformed cursors and non-integer limits; default limit is 20 and accepted range is 1..50. Cursor is an opaque base64url encoding of the destination's final stable sort tuple, decoded and structurally validated server-side; clients never construct or inspect it.

Shared response envelope:
`{ data: { items: readonly T[]; nextCursor: string | null; hasMore: boolean; totalCount?: number } }`

Destination contracts:
- `GET /api/friends?cursor&limit` → `FriendPage`: accepted friend summaries ordered by presence bucket ascending, normalized username ascending, userId ascending. Cursor carries those exact keys. Server derives presence vocabulary only (`online | recently_active | offline`) and participant-owned unread summary; no raw presence precision.
- `GET /api/friends/requests?direction=incoming|outgoing&cursor&limit` → `FriendRequestPage`: pending requests for authenticated requester/recipient only, ordered createdAt descending then requestId descending. Direction is required and validated; incoming and outgoing are separate client destinations/queries.
- `GET /api/friends/study-challenges?role=recipient&status=pending&cursor&limit` → `InvitePage`: authenticated recipient's actionable invites only, ordered createdAt descending then sessionId descending. Reuse 12-02 safe invite DTO; never return snapshot answer keys or foreign participant data.
- `GET /api/friends/messages?cursor&limit` → `ConversationPage`: conversations where authenticated user is a participant, ordered lastMessageAt descending nulls last then conversationId descending. Each item contains safe peer summary, last-message preview, unreadCount, and conversationId; no message body/history collection beyond preview.
- `GET /api/friends/blocks?cursor&limit` → `BlockedPage`: blocks owned by authenticated blocker only, ordered blockedAt descending then blockedUserId descending.

Pagination rule for every destination: query `limit + 1`, return at most `limit`, set `hasMore` from extra row, derive `nextCursor` from last returned row only, and apply strict lexicographic keyset predicates matching complete ORDER BY tuple. Never use offset pagination. Existing message-history `before` cursor remains unchanged and belongs to conversation detail, not Messages destination summaries.
</interfaces>
